Spring Boot ve Katmanlı Mimari ile Yüksek Ölçekli Kurumsal Uygulama Geliştirme

Küçük bir demo veya hobi projesinde tüm mantığı bir Controller içine sıkıştırmak çalışabilir; ancak binlerce personelin izinlerini, özlük haklarını veya kurumsal veri akışlarını yöneten büyük ölçekli bir kamu/kurum projesinde bu yaklaşım sürdürülemez bir felakete dönüşür. Kurumsal seviyede yazılım geliştirmenin anahtarı: Sorumlulukların Katı Ayrımı (Separation of Concerns) ve temiz katmanlı mimaridir.

"Kurumsal yazılımda hız, sadece kodu ilk gün hızlı yazmak değil; 3 yıl sonra gelen yeni bir yasal mevzuat değişikliğini sistemi bozmadan 1 günde entegre edebilmektir."

1. Temiz Katmanlı Mimari: Kim Neden Sorumlu?

Spring Boot projelerinde kabul görmüş standart 4 katmanlı yapı şu şekildedir:

  • Controller Katmanı: Yalnızca HTTP protokolünü konuşur. JSON verisini DTO nesnesine bağlar, gelen parametreleri valide eder (@Valid) ve Service katmanını çağırarak uygun HTTP durum koduyla (200, 201, 204 vb.) yanıt döner. Kesinlikle veritabanı veya iş kuralı (business logic) içermez.
  • Service Katmanı: Uygulamanın kalbidir. İş mantığını, validasyon kurallarını, dış servis çağrılarını ve transaction sınırlarını yönetir. Veritabanı varlıklarını (Entity) DTO'lara dönüştürür.
  • Repository Katmanı: Spring Data JPA arayüzleri ile veritabanı iletişimini sağlar. Özel JPQL sorguları, Native sorgular veya Specifications ile dinamik filtrelemeler burada tanımlanır.
  • Model & DTO Katmanı: Entity sınıfları yalnızca veritabanı tablolarını temsil ederken; Request/Response DTO sınıfları istemciye açık olan alanları taşır. Asla Entity nesneleri doğrudan Controller'dan dışarı sızdırılmamalıdır!
Örnek Katmanlı Akış: 
// 1. Controller
@RestController
@RequestMapping("/api/v1/personnel")
@RequiredArgsConstructor
public class PersonnelController {
    private final PersonnelService personnelService;

    @PostMapping
    public ResponseEntity create(
            @Valid @RequestBody CreatePersonnelRequestDto request) {
        return ResponseEntity.status(HttpStatus.CREATED)
                             .body(personnelService.createPersonnel(request));
    }
}

// 2. Service
@Service
@Transactional
@RequiredArgsConstructor
public class PersonnelService {
    private final PersonnelRepository repository;
    private final PersonnelMapper mapper;

    public PersonnelResponseDto createPersonnel(CreatePersonnelRequestDto dto) {
        // İş mantığı & benzersizlik kontrolleri...
        Personnel entity = mapper.toEntity(dto);
        return mapper.toDto(repository.save(entity));
    }
}

2. Hibernate & Spring Data JPA'da Performans Tuzakları: N+1 Problemi

ORM kütüphaneleri işimizi kolaylaştırsa da arkada ürettiği SQL sorgularını takip etmezseniz sisteminiz prodüksiyonda kilitlenebilir. En yaygın problem: N+1 Sorgu Problemi'dir.

Örneğin 100 personeli listelerken her personelin bağlı olduğu departmanı lazy loading ile çekmeye çalıştığınızda, arka planda 1 adet personel sorgusu ve her biri için ayrı 100 adet departman sorgusu çalışır (toplam 101 sorgu).

Çözüm: JOIN FETCH kullanımı veya @EntityGraph anotasyonu ile ilişkili tabloların tek bir SQL JOIN ile getirilmesini sağlamaktır: 

@Query("SELECT p FROM Personnel p JOIN FETCH p.department WHERE p.active = true")
List findAllActiveWithDepartment();

3. Global Exception Handling: Kontrollü ve Güvenli Hata Yönetimi

Kullanıcıya veya ön yüze Java'nın ham NullPointerException veya SQLException stacktrace'ini göstermek hem kullanıcı deneyimini zedeler hem de ciddi bir güvenlik zafiyetidir.

@RestControllerAdvice kullanarak tüm istisnaları tek bir merkezde yakalayıp standart bir formatta yanıt vermek gerekir: 

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity handleNotFound(ResourceNotFoundException ex) {
        ErrorResponse err = new ErrorResponse(
            HttpStatus.NOT_FOUND.value(),
            ex.getMessage(),
            LocalDateTime.now()
        );
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(err);
    }
}

4. Spring Security ile Stateless JWT Kimlik Doğrulama

Modern kurumsal web uygulamalarında backend, REST API olarak çalıştığından oturum yönetimi sunucu oturumları (session) yerine Stateless JWT (JSON Web Token) ile kurgulanır. Gelen her isteğin Header'ındaki Bearer token çözümlenir, kullanıcının rol ve yetkileri SecurityContext'e atanır. Böylece backend sunucuları yatayda dilediğiniz kadar çoğaltılabilir (stateless horizontal scaling).
